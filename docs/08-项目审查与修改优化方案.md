## 4. 高优先级修改方案

### F01 — 自动更新初始化失败

位置：[updater.js:37](<D:/Aurora Player/app/main/updater.js:37>)。

`autoUpdater.setFeedURL` 传入 `{ url, serverType: 'generic' }`。当前安装的 electron-updater 对象配置读取的是 `provider`，实际抛出 `ERR_UPDATER_UNSUPPORTED_PROVIDER: Unsupported provider: undefined`。外层 catch 随即 return，后面的事件监听、手动检查和安装 IPC、延迟检查均未注册。

**影响：**打包态更新模块无法按设计工作。开发态又会主动提前跳过，普通开发启动无法暴露这个发布缺陷。

修改方案：

- 使用 `{ provider: 'generic', url: UPDATE_FEED }`，或者统一读取打包产物中的更新配置，避免两处配置漂移。
- IPC 总是注册；开发态返回明确的“不支持更新”状态，初始化失败返回错误状态，避免前端调用不存在的 handler。
- 手动检查使用依赖返回的 `isUpdateAvailable`。当前 `!!r.updateInfo` 无法区分“没有新版本”，依赖在这种情况下也返回 updateInfo。
- 主进程保存更新状态快照；关于页进入时读取快照再订阅事件，解决用户晚进入页面错过下载完成事件的问题。
- 检查按钮用 try/catch/finally 恢复状态，处理 IPC 异常。
- 修正文档中“sha512 防篡改，无需签名证书”的表述：来自同一清单的散列只能校验文件与清单一致，不能单独证明发布者身份。更新信任机制和代码签名可独立规划。

验收：用本地测试更新源覆盖无更新、有更新、错误清单、下载失败、已下载后重新进入关于页；至少做一次旧安装版到新安装版升级。不得以 dev 模式通过代替安装态验证。

### F02 — 文件关联打开路径被参数切片丢弃

位置：[main.js:1392](<D:/Aurora Player/app/main/main.js:1392>)，同类逻辑也用于 whenReady 的冷启动文件检测。

两处均使用 `argv.slice(2)`。开发态 `electron . <file>` 有应用入口参数，而常见打包态是 `[exe, file]`；此时切片结果为空。NSIS 已将文件关联到可执行程序，但启动解析会遗漏对应文件。

修改方案：建立唯一的命令行解析函数，根据 `process.defaultApp` 区分入口参数数量，冷启动和 second-instance 共用；过滤已知开关，再识别有效媒体路径。官方明确指出 defaultApp 可用于决定 process.argv 应切掉的参数数量。[Electron process 文档](https://www.electronjs.org/docs/latest/api/process#processdefaultapp-readonly)

验收：未启动/已启动两种状态下双击视频；覆盖路径空格、中文、UNC，以及开发态启动。确认最终播放的是被双击的文件且只保留一个实例。

### F03 — 卸载会删除第三方扩展名注册信息

位置：[installer.nsh:63](<D:/Aurora Player/app/build-resources/installer.nsh:63>)。

安装过程只设置扩展名键的默认值。卸载在该值仍等于 AuroraPlayer.Video 时，却调用 `DeleteRegKey` 删除整个 `.mp4` 等键。键下原有的其他值或子键也可能被删除；仅检查默认值不足以证明整棵键归本程序所有。

修改方案：记录安装前默认值以及本次实际改动的关联；卸载只恢复或删除本程序拥有的值。优先采用应用独立 ProgID 和 OpenWith 注册方式，不覆盖不属于本程序的数据。明确静默更新如何保留关联偏好。

验收：在测试虚拟机预置扩展名额外值、第三方 OpenWith 子键和旧默认值，完成安装/升级/卸载后逐项检查；用户安装后改选其他播放器时，卸载应保留新选择。

### F04 — 清空媒体库只清内存，数据库仍保留旧内容

位置：[main.js:1096](<D:/Aurora Player/app/main/main.js:1096>)、[db.js:139](<D:/Aurora Player/app/main/db.js:139>)。

`library:clear` 将内存数组设为空并调用 saveLibrary；saveLibrary 调用 replaceMedia，但后者只 INSERT OR REPLACE，没有删除未出现的条目。隔离验证中，先写入一个媒体，再 replaceMedia([])，查询仍为 1 条。移除扫描文件夹或删除源文件时也会留下旧数据库记录。

影响：当前页面看似清空，数据库未清空；后续从数据库加载、收藏关联查询等仍可能看到旧内容。启动会触发重扫，因此不要把所有重现都归因于数据库：必须同时区分“保留文件夹配置后按设计重建”和“删除根本没有落盘”。

修改方案：

- 清空动作明确调用数据库清空能力，并取消旧扫描/封面任务，返回真实结果。
- 扫描更新使用扫描批次标记、增量 upsert 和按范围删除；仅在对应目录扫描成功完成后移除未见条目。
- NAS 临时离线不能等同于用户删除媒体；保留条目并标记离线，防止修复过程中引入数据误删。

验收：分别覆盖清空落盘、配置保留后重扫、移除目录、源文件删除、NAS 离线、扫描中途取消；检查内存与数据库一致。

### F05 — 数据库事务异常后没有回滚

位置：[db.js:98](<D:/Aurora Player/app/main/db.js:98>)、[db.js:139](<D:/Aurora Player/app/main/db.js:139>)。

迁移和批量写库均有 BEGIN/COMMIT，但没有异常回滚。隔离验证注入缺少 title 的条目后，下一次写入报 `cannot start a transaction within a transaction`。主进程 saveLibrary 等处又吞掉异常，用户难以知道数据没有保存。

修改方案：统一事务封装，失败执行 ROLLBACK 并向调用层返回错误；迁移标记仅在成功提交后更新；日志包括操作和批次，但避免记录敏感路径。数据库升级使用显式版本和可恢复策略。分清“尚未初始化”“数据为空”“数据库故障”，避免统统返回空数组。

验收：批次中间注入约束错误，确认整个批次未提交、连接可继续写入、界面可见失败；旧 JSON 含坏条目时原文件仍可恢复。

### F06 — mpv IPC 请求可能永久悬挂并堆积

位置：[main.js:223](<D:/Aurora Player/app/main/main.js:223>)、[main.js:532](<D:/Aurora Player/app/main/main.js:532>)。

mpvCommand 将 resolve 保存到 pending，仅收到带 request_id 的回复时删除，没有请求超时。断连、停止播放也没有清理 pending。状态轮询每 500ms 发起 19 个属性查询，用 async setInterval，但没有限制上一次轮询必须完成。

已用“不返回响应的管道”探针观察到请求和 pending 条目保留。100ms 探针只用于展示悬挂；“没有超时/收尾逻辑”来自源码检查，不以这个短观察窗口代替长稳测试。

修改方案：

- 每个请求具有超时、清理函数和会话标识；断连/停止时统一完成所有旧请求。
- 用串行定时轮询或 in-flight 标记，避免轮询重叠；区分命令错误、断连和属性暂不可用。
- 事件稳定后可用 observe_property 减少常态轮询；先保证正确性，再减少 IPC 数量。

验收：不响应、部分响应、中途断管道、用户停止四种场景下，待处理请求在限定时间归零；恢复后没有旧状态覆盖新状态，轮询并发批数不超过 1。

### F07 — 播放切换和子进程重启缺少身份隔离

位置：[main.js:161](<D:/Aurora Player/app/main/main.js:161>)、[main.js:621](<D:/Aurora Player/app/main/main.js:621>)、[main.js:661](<D:/Aurora Player/app/main/main.js:661>)、[main.js:720](<D:/Aurora Player/app/main/main.js:720>)。

主要风险链：

- 两次 startPlayback 都可在 await cleanupPlayback 后继续执行，没有取消令牌或序列号保证只启动最终请求。
- 旧 mpv 的 exit 回调无条件把全局 mpvProc 置空；超时放行后旧进程晚退出，可能覆盖新进程引用。
- resetSession 主动销毁 pipe，也会触发 close→retry；旧连接重试任务没有按会话取消。
- 修改 DLNA 设置时 kill 后立即启动新进程，旧进程 exit 回调仍无条件将 dlnaProc 置空并标记停止。
- mpv 意外退出只置空引用，没有实现 README 声称的“崩溃自动恢复”；反复重连同一管道不等于重启播放器。

修改方案：引入 PlaybackSession，集中持有进程、管道、计时器、请求、缩略图任务和当前文件；每次切换生成 generation，所有异步回调先验证身份；启动串行化或明确采用“最后一次请求生效”。DLNA 重启也要等待旧进程退出并比较进程身份。异常退出实现有上限的退避恢复，保留位置，区分正常停止。

验收：连续快速 A→B→C、启动中停止、播放中关闭、进程晚退出、DLNA 连续改名/开关；最终只有目标进程，停止后没有重连任务，界面与实际进程状态一致。具体竞态触发概率仍需集成验证。

### F08 — DLNA 网络访问边界不完整

位置：[httpd.js:11](<D:/Aurora Player/app/dlna/httpd.js:11>)、[httpd.js:228](<D:/Aurora Player/app/dlna/httpd.js:228>)、[main.js:700](<D:/Aurora Player/app/main/main.js:700>)。

已确认两条入口问题：

- assertLanUrl 只过滤字面 IP，所有域名直接返回 true，未解析并检查最终地址。隔离 SOAP 请求中的 outside.example 被接受并转为 load 命令，违反仓库“仅局域网”的规则。
- GENA CALLBACK 未做相同地址校验，直接交给 http.request。隔离测试证实外部示例地址会进入 NOTIFY 传输；实际网络已用替身阻断。

此外，HTTP 监听未指定接口；创建防火墙规则时没有显式配置专用网络、本地子网来源和程序路径。实际可达范围取决于主机网络、防火墙权限和已有规则，本次没有证明公网可达。

修改方案：

- 媒体 URI 与 CALLBACK 共用地址策略：限制协议、解析全部 A/AAAA、验证实际连接地址，默认匹配受信网络/控制端。
- 处理 DNS 结果变化、重定向和媒体播放列表的二次请求。只在入口 DNS 检查一次不足以约束 mpv 后续访问；按需求选用受控媒体代理或引擎网络限制，并明确可支持的网络格式。
- CALLBACK 默认限制为控制端地址或已授权局域网地址；限制订阅数量、每个订阅的回调数、通知并发和重试预算。
- 防火墙规则显式限定专用网络、程序和所需端口，处理端口变化；权限不足时展示可理解的状态和操作指引。

验收：公网 IP、域名解析至公网/禁止地址、混合 A/AAAA、重定向、未授权 CALLBACK、订阅洪泛均被正确处理；合法 NAS 域名和本地供片仍可使用。

### F09 — 标准 GENA 续订返回 412

位置：[httpd.js:251](<D:/Aurora Player/app/dlna/httpd.js:251>)。

### F10 — 媒体库工作阻塞主进程，封面完成反复写全库

位置：[main.js:876](<D:/Aurora Player/app/main/main.js:876>)、[main.js:900](<D:/Aurora Player/app/main/main.js:900>)、[main.js:936](<D:/Aurora Player/app/main/main.js:936>)。

修改方案：

- 将扫描、刮削和数据库批处理移入后台 worker/utility process，提供进度、取消、失败目录与重试。
- 主窗口先显示缓存数据，再后台增量扫描；扫描结果按批提交。
- 封面成功只更新对应记录，合并推送变化；给任务加去重、扫描批次标记和播放期间资源预算。
- 队列统一处理超时、完成只执行一次、进程回收；磁盘/图片缓存设容量与清理规则。
- 当前深度 4 和约 2000 条的软限制应明确呈现“扫描不完整”，不要将结果静默当成全库。

验收：用本地大库和慢速/离线 NAS 分别测首窗时间、输入响应、扫描吞吐、数据库写入次数；扫描中仍能暂停/切片/退出。先记录基线，再设优化幅度，不能根据代码结构宣称已经提升多少倍。

## 7. 结构与性能优化路线

### 7.1 按故障边界拆主进程

不建议一开始全量重写。先用回归用例固定行为，再按职责逐步移动代码：

| 建议模块 | 负责什么 | 对外接口示例 |
| --- | --- | --- |
| PlaybackSession | 单次播放状态、切换、取消与恢复 | open / stop / retry / snapshot |
| MpvTransport | 管道、超时、请求清理、属性订阅 | command / observe / dispose |
| LibraryService | 扫描批次、增量写库、离线状态、后台任务 | scan / cancel / changes |
| CoverService | 封面/缩略图去重、资源预算和缓存 | enqueue / cancelSession / evict |
| DlnaManager | 进程身份、启动停止、控制权与协议状态映射 | start / stop / restart |
| SettingsRepository | 字段验证、原子保存、版本迁移 | read / patch |
| UpdateService | 更新状态快照、检查与安装 | status / check / install |

划分标准是“一类生命周期和失败由一个模块负责”，不是每个函数都包一层对象。主入口最终只组合这些模块和窗口事件。

### 7.2 数据与设置治理

- 设置采用临时文件写入后原子替换，保留最近一次有效版本；保存失败不能仍报告成功。
- 数据库语句复用，批量事务；记录位置按变化与合理间隔节流，暂停/停止时补一次，避免每个轮询都同步写相同值。
- 收藏、播放列表区分库外媒体和失效路径；playlist_items 的外键/删除事务等完整性约束可在数据库升级批次统一补齐。
- 日志分级、轮转、有限容量；用会话 ID 关联 UI→主进程→mpv→DLNA；导出诊断时脱敏 URL 凭据和媒体路径。

### 7.3 渲染与视觉优化

当前视觉引擎已有部分隐藏暂停和 reduced-motion 处理，不能笼统判定为“完全没有节能”。后续重点是统一预算：

- 播放、暂停、首页、设置、最小化分别设动画和抽帧预算，优先保障视频。
- 用性能记录判断双外观 resolve、样式写入、多个动画循环的真实成本；按参数变化更新，避免时间位置变化触发无关重算。
- 大库展示按数据规模采用分页/虚拟列表，图片缩略尺寸与懒加载；先消除全量数据更新链路。
- logo 约 917 kB，可在保留视觉清晰度前提下生成适当尺寸的资源；再评估页面延迟加载，处理无效动态导入提示。
- 错误操作显示“失败原因/重试”，网络不可达、扫描不完整、更新不可用使用不同状态。
- 空按钮式开关补足语义名称、键盘可操作和焦点状态；对比度、缩放和弹层焦点做界面验收。本次未做截图或屏幕阅读器测试，不预判整体视觉质量。
